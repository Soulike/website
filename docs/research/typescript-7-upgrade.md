# TypeScript 7 upgrade assessment

- Research date: 2026-11-01.
- Repository baseline: [`9014815fab5c7e83ef334086ae5620fc390356e2`](https://github.com/Soulike/website/commit/9014815fab5c7e83ef334086ae5620fc390356e2).
- Local environment: Node.js 26.13.0, pnpm 12.16.1, macOS; the existing dependency graph uses TypeScript 5.9.3.

This assessment answers whether the whole project can adopt TypeScript 7. It records an investigation, rather than an implemented compiler migration. The dependency release-age policy is owned by [`pnpm-workspace.yaml`](../../pnpm-workspace.yaml).

The migration target was subsequently changed to TypeScript 6. The
[TypeScript 6 migration record](typescript-6-migration.md) describes the delivered
change and validation; the findings below retain the pre-migration baseline.

## Conclusion

**Replacing every `typescript` dependency with TypeScript 7 is currently blocked by the lint and Jest integrations.** The installed `typescript-eslint` and `ts-jest` actively reject TypeScript 7's missing legacy JavaScript compiler API. These are observed runtime failures, beyond unsupported peer ranges.

**Using TypeScript 7 for project type checking while retaining a compatible JavaScript compiler API for those integrations is feasible in principle.** The compiler probes found configuration-default changes that can be addressed without changing business logic. A complete dependency installation, lint run, Jest transformation, and container build using that arrangement remain necessary before claiming a delivered migration.

## Available release and API

The [official npm registry](https://registry.npmjs.org/typescript) reports `typescript@7.0.2` as `latest`, published on 2026-07-08, and `7.1.0-beta` as `beta`. The stable release has already passed this project's seven-day release-age threshold. The [TypeScript 7 release announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) confirms that the native compiler is available through the ordinary `typescript` package and retains the `tsc` command. Existing scripts do not need a rename to `tsgo`.

The [published 7.0.2 manifest](https://registry.npmjs.org/typescript/7.0.2) exports its top-level module through `lib/version.cjs`, alongside separate `unstable` API paths. Loading that top-level module locally returns only `version` and `versionMajorMinor`; `createProgram` and `ScriptTarget` are absent. The presence of new experimental API paths does not make existing integrations compatible with the old API.

## Local compiler and integration evidence

TypeScript 7.0.2 was installed in a temporary pnpm project. Its executable was invoked against the current checkout and existing dependency graph, without replacing the checkout's TypeScript dependency or changing source/config files.

| Probe                                                                                                                  | Result                | What it establishes                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript 5.9.3 baseline: 31 package checks with `--noEmit`, plus three web solutions with `-b --force`               | 34/34 passed          | The checked project configurations pass with the current compiler.                                                                                                                                                            |
| Same checks with TypeScript 7.0.2 and original configurations                                                          | 24/34 passed          | A direct compiler switch exposes ten failing configurations.                                                                                                                                                                  |
| Recheck failures with explicit ambient types; each web app/node config checked separately                              | 13/13 passed          | The observed type failures can be resolved through ambient-type configuration and the CSS declaration described below. This recheck uses `-p --noEmit` for web configs, rather than rerunning their complete solution builds. |
| Process-local module substitution: installed `typescript-eslint` receives the actual TypeScript 7.0.2 top-level module | Import throws         | Confirms the installed lint integration rejects TypeScript 7.                                                                                                                                                                 |
| Equivalent substitution for `ts-jest`'s resolved compiler module, followed by `ConfigSet` initialization               | Initialization throws | Confirms the installed transformer rejects the missing compiler API.                                                                                                                                                          |

The ten failing configurations were the smoke scripts, database legacy server, all three web apps, `async-helpers`, `test-helpers`, `i18n`, `react-components`, and web `model`.

Most failures came from the new `types: []` default: Node module/global declarations were no longer automatically included, which also removed assertion narrowing and inherited EventEmitter members. Explicit `types: ["node"]` resolved those diagnostics; the database legacy server needed `["node", "jest"]`. The [release announcement's configuration changes](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#updates-since-5x-and-new-behaviors-from-60) explain this default.

`react-components` additionally reported TS2882 for `@library/markdown-article-renderer/style.css`, because `noUncheckedSideEffectImports` now defaults to true. A temporary config overlay containing an ambient declaration for that exact module passed with the check still enabled. Disabling the check was used only to confirm the cause; an asset declaration is the demonstrated corrective direction.

The API probes substituted module loading only inside separate Node processes. They did not modify `node_modules` links or perform a full upgraded workspace installation. The observed failures agree with the integrations' published source guards, but do not validate a proposed compatibility dependency graph.

## Migration boundary

Microsoft documents a [side-by-side arrangement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-60): alias `@typescript/typescript6` as `typescript` for API consumers and alias the native `typescript` package as `@typescript/native`. The [compatibility package](https://registry.npmjs.org/@typescript/typescript6/6.0.2) provides the old API and `tsc6`; the native package provides `tsc`, avoiding executable-name conflicts.

That is a migration option, rather than a validated one-command change for this repository. The installed React lint plugin and older nested lint packages constrain a TypeScript 6 API dependency, so their graph must be reconciled. Retaining TypeScript 5.9.3 as the API provider is another possible pilot boundary, but both packages then provide a `tsc` binary: the native executable must be selected explicitly and its ownership verified in each workspace and CI environment.

A future implementation should resolve the API-provider graph, add explicit ambient types and asset declarations, then verify the actual selected compiler with full workspace checks, web builds, lint, existing tests, and container CI. This assessment has not selected or implemented that migration.

## Platform and validation limits

The application Dockerfiles use `node:lts-alpine`, and the image workflow targets `linux/amd64`. The [published Linux x64 compiler package](https://registry.npmjs.org/@typescript/typescript-linux-x64/7.0.2) contains an ELF executable that `file` identifies as statically linked. Inspecting its ELF program headers found neither `PT_INTERP` nor `PT_DYNAMIC`; this artifact does not depend on a glibc dynamic loader. That removes the specific glibc-loader concern, but no TypeScript 7 Alpine container build was run.

The ordinary `pnpm validate:pr` passed with the current TypeScript 5.9.3 dependency graph and the seven-day policy. The TypeScript 7 probes establish compiler compatibility for the exercised configurations and changes, not a complete migration, production deployment, upgraded Jest execution, or editor language-service validation. No new unit tests were added. Recheck release metadata, integration support, and these probes when an upgrade is implemented.
